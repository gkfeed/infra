# API contract

Target API contract approved on 2026-09-04.

| Table | Columns | API access | Owner | Keys |
| --- | --- | --- | --- | --- |
| `users` | `id`, `name`, nullable `hashed_password` | Read; update password hash | API | PK `id`; unique `name` |
| `feed` | `id`, `title`, `url`, `type`, `user_id` | Read, insert, delete | API | PK `id`; FK `user_id -> users.id`; unique `(user_id, url, type)` |
| `item` | `id`, `feed_id`, `title`, `text`, `date`, `link` | Read and delete | Shared: Parser creates, API deletes | PK `id`; FK `feed_id -> feed.id ON DELETE CASCADE` |
| `webauthn_credentials` | `id`, `user_id`, `credential`, `name`, `created_at`, `last_used_at` | Read, insert, update, delete | API | PK `id`; FK `user_id -> users.id` |
| `refresh_tokens` | `id`, `user_id`, `expires_at`, `created_at` | Read, insert, delete | API | PK `id`; FK `user_id -> users.id` |
| `browser_sessions` | `token_hash`, `user_id`, `created_at`, `last_seen_at`, `expires_at` | Read, insert, update, delete | API | PK `token_hash`; FK `user_id -> users.id ON DELETE RESTRICT`; indexes `user_id`, `expires_at` |
| `item_changes` | `id`, `user_id`, `item_id`, nullable `payload`, `changed_at` | Read | Database triggers write; API reads | PK `id`; index `(user_id, id)` |

Integer IDs use `INTEGER GENERATED BY DEFAULT AS IDENTITY`, so applications
may generate IDs or supply them explicitly.
User names are non-null and unique. Password hashes may be null for users who
have no password. Feed fields are non-null. A user may add the same URL under
different feed types, but may not repeat the same URL and type. Different
users may add the same URL and type.

Shared parser text columns are non-null. Contract timestamps use
`TIMESTAMPTZ`. WebAuthn credential IDs use `BYTEA`; serialized credential JSON
uses `TEXT` so PostgreSQL preserves the API representation unchanged.

The parser may read feeds and create items. The API may read and delete items.
The parser never deletes items. Deleting a feed cascades to its items in the
database schema.

The API does not run data migrations at startup. The canonical token table is
`refresh_tokens`.

Migration `20261012101552` adds browser cookie sessions for
[API PR #7](https://github.com/gkfeed/api/pull/7). `token_hash` is a 32-byte
SHA-256 digest of the random 256-bit cookie identifier; the raw identifier is
never stored. All five columns are non-null. Timestamps use `TIMESTAMPTZ`, with
`last_seen_at >= created_at` and `expires_at > created_at`.

The API supplies creation and expiry timestamps. Authentication atomically
checks the 30-day inactivity and 90-day absolute deadlines and advances
`last_seen_at` without changing `expires_at`. These deadlines are API policy;
the database enforces the timestamp ordering above. Current logout deletes by
digest; logout-all deletes by `user_id`. `UPDATE` is required for activity
renewal and does not change the grants on `refresh_tokens`. The API receives
no DDL privileges or object ownership. See the
[browser session rollout](../docs/browser-sessions.md) for release ordering,
maintenance, and the forward-only rollback policy.

Migration `20260927071753` adds `item_changes` for the item sync API. The API
reads changes for its authenticated user with `WHERE user_id = ? AND id > ?`
ordered by `id`. `payload` is JSONB with `ID`, `FeedID`, `Title`, `Text`, `Date`,
and `Link` for inserts and updates. A null `payload` is a deletion tombstone.
Triggers record direct item deletion and deletion through a feed cascade. The
database holds a transaction advisory lock per user before allocating change
IDs, so committed changes for one user appear in ID order. The API has only
`SELECT` on this table and no access to its identity sequence. Change history
must remain available until the API has a cursor expiry and recovery policy.
